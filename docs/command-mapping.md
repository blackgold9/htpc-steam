# Command Mapping

This integration targets a **gaming-focused** SteamOS/Bazzite HTPC (Steam/Gamescope), not media playback — unlike upstream's Windows HTPC use case, which assumed a movie/TV box. That distinction drove real scope decisions below: media transport controls (play/pause/rewind/etc.) were dropped entirely rather than ported, since they don't serve gaming and were never going to be exercised. See `../integration/src/uc_intg_steamos/entities/remote.py` and `media_player.py`'s docstrings for where this shows up on the Remote side.

Windows `HTPC_Agent.exe` command vocabulary → SteamOS/Gamescope mechanism implemented by `plugin/py_modules/uc_steamos_agent/commands/dispatcher.py`. Keep this in sync with the dispatcher's alias table. Confidence levels reflect what's been verified on real Bazzite/Gamescope hardware vs. still assumed.

| Category | Windows command(s) | SteamOS mechanism | Confidence |
|---|---|---|---|
| Nav | `arrow_up/down/left/right`, `enter`, `escape`, `back`(→esc), `tab`, `space`, `delete`, `backspace`, `home`, `end`, `page_up/down` | uinput `KEY_*` | **Confirmed on real hardware** — `arrow_down`/`arrow_up`/`enter`/`escape` sent via a live uinput virtual keyboard visibly drove Big Picture navigation and selection (A-button-style confirm on `enter`) on the Bazzite/Gamescope test box, 2026-08-22 |
| Volume | `volume_up/down`, `mute`, `mute_toggle`, `set_volume:N` | `wpctl set-volume`/`set-mute @DEFAULT_AUDIO_SINK@ ...` | **Confirmed on real hardware** — `volume_up`/`volume_down`/`set_volume:N`/`mute` all verified via `wpctl get-volume` before/after on the test box, 2026-08-22. Required a fix: the plugin runs as root (for uinput), but `wpctl` needs the desktop user's `XDG_RUNTIME_DIR` to reach PipeWire — see `commands/user_session.py` |
| Gamescope hotkeys | `windows_key` → `steam_home`; new `steam_qam` | Ctrl+1 (Steam button), Ctrl+2 (Quick Access Menu), Ctrl+6 (L3) via uinput combo | **Confirmed on real hardware** — `steam_qam` visibly opened and (via `escape`) closed the Quick Access Menu on the test box, 2026-08-22. `steam_home`/`steam_l3` implemented but not yet individually tested |
| Windows Meta shortcuts | `win_r`, `win_d`, `win_l`, `win_i`, `alt_tab`, `ctrl_shift_esc`, `ctrl_alt_del` | **Dropped**: `win_d`/`win_l`/`ctrl_alt_del` — Gamescope's hotkey handler intercepts and discards Left-Windows/Super combos (`LMOD_GUI`) before apps see them. `alt_tab` kept for Desktop-Mode-only use. `win_i` → `steam_settings`, see the Steam URIs row below. | Drop for Meta combos confirmed (Gamescope bug-tracker discussion) |
| Steam URIs | `win_i` → `steam_settings`; new `steam_library` | `steam <uri>` (`steam://open/settings`, `steam://open/games`) | **Confirmed on real hardware** (2026-08-23): both genuinely open the right Steam screen. `steam_settings` needs `escape` pressed **twice** to fully close (nested menu depth) — a single press only backs out one level. `steam_home` (Ctrl+1) sent from within it did not return home either, opening a side overlay instead — treat `steam_home` as reliable only from the main Big Picture view, not from arbitrary nested screens |
| Close last launch | *(new, no Windows equivalent)* `close_last_launch` | SIGTERM to the process group of the most recently `steam_uri`-launched pid | Implemented as a safety valve alongside the Steam URI commands above; not separately live-tested since both are already known to close cleanly via `escape` |
| Exiting a game | *(new, no Windows equivalent)* `steam_overlay`, `alt_f4`, `force_quit_game` | Three separate, explicit escalation-tier commands, deliberately not auto-chained (from the 2026-08-23 grilling session): `steam_overlay` = Shift+Tab (Steam's in-game overlay toggle, then the user navigates to Exit); `alt_f4` = uinput Alt+F4 combo (OS-level graceful close request); `force_quit_game` = find a process with `SteamAppId` set in its environment (`commands/game_control.py`, the standard Proton/Steamworks marker for "launched by Steam", found via the same `/proc`-scanning technique as `user_session.py`) and SIGTERM its process group | **All three confirmed on real hardware** (2026-08-23), tested against an actual running game (Bopl Battle via Proton), not just a menu: `SteamAppId` genuinely is set on every process in the game's tree (reaper, the Proton/pressure-vessel wrapper chain, `BoplBattle.exe`, its crash handler); `steam_overlay` visibly toggled Steam's UI chrome on and off over the running game (process list unchanged, confirming it doesn't disturb the game); `alt_f4` **fully and gracefully closed the game** with zero orphaned processes; `force_quit_game` **fully tore down the whole tree**, including two other process groups the killed one didn't directly own (see below) — landing cleanly back at the Big Picture home / the game's Steam page respectively, no crash dialogs either time. One real design assumption corrected along the way: the game's process tree spans **three separate process groups** (reaper+bwrap; the Proton/pressure-vessel wrapper chain; the actual game binary), not one shared group as the docstring speculated — yet killing just the first one's group still took the whole tree down, almost certainly because bubblewrap's sandbox teardown cascades to everything running inside it, not because of process-group semantics. Also found: the box's `magick x:root` screenshot tool (docs/hardware-notes.md) only captures the primary/Big-Picture XWayland surface — actual in-game content renders black in a capture, consistent with Steam's `STEAM_MULTIPLE_XWAYLANDS=1` using a separate XWayland instance per game; a real, separate limitation of the screenshot tooling, not a bug in these commands |
| Getting into a game | *(new, no Windows equivalent)* `launch_game:<appid>` | `steam <uri>` (`steam://rungameid/<appid>`) — same launch mechanism as the fixed Steam URI shortcuts above, just with a dynamic appid | **Confirmed on real hardware** (2026-08-23), twice: `launch_game:1686940` (Bopl Battle) genuinely launched the game (`BoplBattle.exe` visible in the process tree within a few seconds) both directly against the agent's `/command` endpoint and through the integration's `SteamOSDevice.launch_game()` -> `SteamOSClient` -> agent path, and `force_quit_game` cleanly tore it back down each time — the full launch→exit loop verified end-to-end at both the agent and integration layers. The appid list itself comes from `GET /games` (`docs/protocol.md`), built from `localconfig.vdf`'s `LastPlayed` field cross-referenced against installed `appmanifest_*.acf` files (recents-first, per the grilling session; Favorites turned out not to be locally extractable — see `docs/hardware-notes.md`). Compat tools (Proton, Steam Linux Runtime, redistributables) get a `LastPlayed` entry too and are filtered out by name. On the Remote side, this is a dedicated Game Launcher media_player entity (`entities/game_launcher.py`, separate from the monitoring dashboard's media_player) whose `SOURCE_LIST` is refreshed from `/games` every poll cycle and whose `SELECT_SOURCE` triggers the launch. Pairing with a real UC Remote 3 confirmed 2026-08-23 (`integration/README.md`'s Status section): the entity comes up `ACTIVE`/`CONNECTED` on the Remote; actually pressing a game in `SOURCE_LIST` on-device (vs. only through the API/device layer) is the one link in this chain not yet exercised, since that requires the entity to be added to a page on the physical Remote first |
| Power | `power_sleep`, `power_hibernate`, `power_shutdown`, `power_restart` | `systemctl suspend/hibernate/poweroff/reboot`, fired ~200ms after the HTTP response via a background timer so the response reaches the client before the host goes offline | Implemented (Phase 2 dispatcher) with unit tests for the deferred-fire behavior; **not yet live-tested** (disruptive, deferred by user request) — root execution means no polkit friction is expected (unlike the plain-SSH-user `systemctl reboot` attempt in docs/hardware-notes.md, which needed interactive auth), but this is still unconfirmed live. Hibernate still expected to fail on a typical swap config |
| Wake-on-LAN | `POWER_ON` (remote-entity special command) | Unchanged — client-side WoL, never touches the agent | Same as upstream |
| Function keys | `f1`..`f12` | uinput `KEY_F1`..`KEY_F12` verbatim | Trivial |

## Deliberately not implemented

**Media transport controls** (`play_pause`, `play`, `pause`, `stop`, `previous`, `next`, `fast_forward`, `rewind`, `record`) were built in Phase 1 (uinput `KEY_PLAYPAUSE` etc.), then removed (2026-08-23) once the project's actual purpose was clarified: this is a gaming HTPC, not a media/movie box like upstream's Windows target. They were never live-tested and don't serve gaming, so rather than carry dead, unverified surface forward, they were cut along with their Remote-side page (`_create_media_page` → `_create_volume_page`, keeping only volume/mute) and `media_player.py`'s no-op `PLAY_PAUSE`/`STOP`/`NEXT`/`PREVIOUS` handling. Volume controls were kept since they're genuinely useful regardless of gaming vs. media. The `media_player` entity itself stays — it's purely a UI vehicle for the system-monitoring dashboard (temps/load/network), not actual media control.

**Virtual gamepad input** (button/axis emulation for actual in-game control, as opposed to keyboard-driven Steam UI navigation) was considered during this same reframing and deliberately deferred, not built — a real uinput undertaking (buttons + analog axes, mapping the Remote's physical buttons to them) that's out of scope for this cleanup. If gaming use reveals that keyboard-only input isn't sufficient for in-game control (as opposed to just navigating Steam's own UI, which is confirmed keyboard-friendly), this is the natural next phase.

**General-purpose app/URL launching** (`launch_exe:PATH`, `launch_url:URL`, `shortcut:<name>`, and the upstream commands that would have mapped to them — `custom_calc`/`custom_notepad`/`custom_cmd`/`custom_powershell`, `url_youtube`/`url_netflix`/`url_plex`/`url_jellyfin`, `pair_bluetooth`) was built, live-tested, and then **removed** (2026-08-23) after finding a real, unrecoverable gap: opening a web URL via `xdg-open` took over Gamescope's UI full-screen, and no command available to the agent — `escape`, `alt_tab`, `steam_home`, or a purpose-built `close_last_launch` (process-group SIGTERM) — could get back to Gamescope. This stranded the user twice; actual recovery required their own physical Alt+F4 or a mouse/touch-driven UI flow (tap avatar → Steam button → Home) that a virtual keyboard can't replicate.

The code (`commands/launch.py`, `commands/shortcuts.py`) is preserved in git history (see the "Phase 4" and its follow-up trim commits) if this is revisited later — candidates for actually solving it: virtual mouse/touch support (uinput supports this, just not built here), or finding an actual keyboard-reachable path to that recovery overlay. Until then, don't re-add `launch_url`/`launch_exe`/`shortcut` without addressing this.

`steam_settings`/`steam_library` (Steam URI row above) are kept because they're confirmed to open and close cleanly — the gap is specific to launching content *outside* Steam's own UI (a real browser window), not to `steam://` URIs in general.
