# Command Mapping

Windows `HTPC_Agent.exe` command vocabulary → SteamOS/Gamescope mechanism implemented by `plugin/py_modules/uc_steamos_agent/commands/dispatcher.py`. Keep this in sync with the dispatcher's alias table. Confidence levels reflect what's been verified on real Bazzite/Gamescope hardware vs. still assumed.

| Category | Windows command(s) | SteamOS mechanism | Confidence |
|---|---|---|---|
| Nav | `arrow_up/down/left/right`, `enter`, `escape`, `back`(→esc), `tab`, `space`, `delete`, `backspace`, `home`, `end`, `page_up/down` | uinput `KEY_*` | **Confirmed on real hardware** — `arrow_down`/`arrow_up`/`enter`/`escape` sent via a live uinput virtual keyboard visibly drove Big Picture navigation and selection (A-button-style confirm on `enter`) on the Bazzite/Gamescope test box, 2026-08-22 |
| Media | `play_pause`, `play`, `pause`, `stop`, `previous`, `next`, `fast_forward`, `rewind`, `record` | uinput `KEY_PLAYPAUSE` etc. | Implemented (Phase 1 dispatcher), **not yet on-device tested** — no active media player was running during the Phase 1 hardware session to observe against |
| Volume | `volume_up/down`, `mute`, `mute_toggle`, `set_volume:N` | `wpctl set-volume`/`set-mute @DEFAULT_AUDIO_SINK@ ...` | **Confirmed on real hardware** — `volume_up`/`volume_down`/`set_volume:N`/`mute` all verified via `wpctl get-volume` before/after on the test box, 2026-08-22. Required a fix: the plugin runs as root (for uinput), but `wpctl` needs the desktop user's `XDG_RUNTIME_DIR` to reach PipeWire — see `commands/user_session.py` |
| Gamescope hotkeys | `windows_key` → `steam_home`; new `steam_qam` | Ctrl+1 (Steam button), Ctrl+2 (Quick Access Menu), Ctrl+6 (L3) via uinput combo | **Confirmed on real hardware** — `steam_qam` visibly opened and (via `escape`) closed the Quick Access Menu on the test box, 2026-08-22. `steam_home`/`steam_l3` implemented but not yet individually tested |
| Windows Meta shortcuts | `win_r`, `win_d`, `win_l`, `win_i`, `alt_tab`, `ctrl_shift_esc`, `ctrl_alt_del` | **Dropped**: `win_d`/`win_l`/`ctrl_alt_del` — Gamescope's hotkey handler intercepts and discards Left-Windows/Super combos (`LMOD_GUI`) before apps see them. `win_i` → `steam://open/settings` (implemented as `steam_settings`). `alt_tab` kept for Desktop-Mode-only use. | Drop for Meta combos confirmed (Gamescope bug-tracker discussion). **`steam_settings` confirmed on real hardware** (2026-08-23): `steam://open/settings` genuinely opens Steam's Settings screen. Two real nuances found live: a single `escape` did **not** fully close it (needed two — the screen has nested menu depth); `steam_home` (Ctrl+1) sent *from within* Settings did not return to the main view either — it opened a side overlay instead, rather than acting as a universal "go home" shortcut in every context. Recovery required manually backing out. Treat `steam_home` as reliable only from the main Big Picture view, not from arbitrary nested screens, until tested further |
| System apps | `custom_calc`, `custom_notepad`, `custom_cmd`, `custom_powershell` | Folded into the shortcuts mechanism instead of 4 fixed buttons; cmd/powershell → attempt `konsole`/`xterm` launch | Research spike — floating utility windows while remaining in Game Mode is unverified |
| Web URLs | `url_youtube`, `url_netflix`, `url_plex`, `url_jellyfin` | Folded into the shortcuts mechanism, seeded with `xdg-open <url>` fallback files | **Confirmed working, with an unresolved recovery gap** (2026-08-23): `xdg-open` failed outright with only `XDG_RUNTIME_DIR` set (fell through every graphical-open helper to absent text browsers) — fixed by extending `user_session.session_env()` to also copy `DISPLAY`/`DBUS_SESSION_BUS_ADDRESS`/`XDG_CURRENT_DESKTOP`/`XDG_DATA_DIRS` from a live session process (found via `/proc` scan, not hardcoded). After the fix, `launch_url:https://youtube.com` genuinely opened YouTube in Firefox — **twice**, both times full-screen, replacing Gamescope's UI entirely. **No remote recovery path was found.** `escape`/`alt_tab`/`steam_home` all failed to return to Gamescope. Built `close_last_launch` (SIGTERM to the launched process's group) as a mitigation, but it *also* failed — strong evidence Firefox is not a child of the `xdg-open` call at all, but a pre-existing/D-Bus-activated instance our launch just messaged. The user's actual manual recovery is a **mouse/touch-driven UI flow** (tap avatar top-right → tap the Steam button that appears at the bottom → Home in the left menu) — not a keyboard shortcut our virtual keyboard can replicate. **This stranded the user twice** and is a real, unresolved gap, not just an unverified assumption. Do not expose `launch_url` for arbitrary web content on the Remote's default button layout without either solving this (candidates: a virtual mouse device to replicate the tap sequence, since we don't yet have virtual-mouse uinput support; or discovering an actual keyboard-reachable path to that same overlay) or prominently warning that physical access may be required to recover |
| Power | `power_sleep`, `power_hibernate`, `power_shutdown`, `power_restart` | `systemctl suspend/hibernate/poweroff/reboot`, fired ~200ms after the HTTP response via a background timer so the response reaches the client before the host goes offline | Implemented (Phase 2 dispatcher) with unit tests for the deferred-fire behavior; **not yet live-tested** (disruptive, deferred by user request) — root execution means no polkit friction is expected (unlike the plain-SSH-user `systemctl reboot` attempt in docs/hardware-notes.md, which needed interactive auth), but this is still unconfirmed live. Hibernate still expected to fail on a typical swap config |
| Wake-on-LAN | `POWER_ON` (remote-entity special command) | Unchanged — client-side WoL, never touches the agent | Same as upstream |
| Bluetooth | `pair_bluetooth`, `show_pairing_help` | `show_pairing_help` ports verbatim (canned text, no OS dependency); `pair_bluetooth` — research spike, may drop | — |
| Launch | `launch_exe:PATH`, `launch_url:URL` | `subprocess.Popen`, `steam <uri>`, or `xdg-open` | `launch_url` implemented and confirmed working, but see the Web URLs row above for the unresolved no-recovery-path finding. `launch_exe` implemented, not yet live-tested — genuinely uncertain whether it shares the same recovery gap, since a freshly-`Popen`'d process (e.g. `konsole`) is actually our child, unlike Firefox's D-Bus-relayed case |
| Shortcuts | `shortcuts\*.lnk` bare-filename | Plain files under the plugin's settings dir, keyed by name | **Deviation from upstream**: the wire convention changes to `shortcut:<name>` instead of a bare filename, since a bare name was ambiguous against the fixed vocabulary |
| Function keys | `f1`..`f12` | uinput `KEY_F1`..`KEY_F12` verbatim | Trivial |

Rows marked "Research spike" are expected to be resolved (confirmed, adjusted, or dropped) during Phase 4 on-device testing — see the plan's verification checklist.
